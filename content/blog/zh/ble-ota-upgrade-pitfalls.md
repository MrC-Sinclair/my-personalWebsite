## 引子：业务通道跑得好好的，为什么 OTA 这么难

2026 年 11 月 3 日到 6 日，我几乎都在和一块 BLE 子固件死磕。

在此之前，设备的业务通道一直很稳定：小程序通过 BLE 发 JSON，载荷走 AES-128-ECB 加密，设备回包也是同样的格式，通知、分包、回执都跑得很顺。但 OTA 完全是另一套东西——设备进入 FlashBoot 后，同一根 GATT 特征上突然换成 `A5 5A` 开头的明文二进制帧，既不加密，也不是 JSON。

更麻烦的是，升级不是“把文件推过去”这么简单：

- 设备要先在正常固件里收到 `ota_start`，处理完保存、静音、TWS 复查等前置动作，才回 `ota_start_ack`；
- 收到 `ok` 后设备会主动断开，再以 FlashBoot 的身份重新上线；
- FlashBoot 不保证携带正常模式的广播标识，重连只能靠升级前保存的 `deviceId`；
- 连上之后还不能马上发数据，要等通知订阅真正就绪，等 boot 的 `0x10` 广播，再按它发起的 `0x50` 数据请求一段一段回填；
- 传完之后还要重连回正常固件，读 `firmwareVer` 核对版本，才算真的成功。

而 iOS、鸿蒙、Android 对 BLE 的缓存策略、GATT 句柄、写模式又各有一套脾气。同样是“连接成功”，在 iOS 上可能只是拿到了连接句柄，通知通道根本没通；同样是“写入成功”，在无响应写模式下也只代表数据交给了协议栈，不代表设备收到了。

这篇文章不复述完整协议，而是把这次踩到的坑按主题拆开：身份、UUID、句柄、写模式、时序、MTU、无响应、性能。每个坑都写清楚我们最后是怎么判断、怎么落地的，方便后面做 BLE OTA 的人少走几天弯路。

## 一、先把整体时序串起来

整个流程可以压缩成下面这条链路：

```text
正常固件（JSON + AES）
  │
  ├─ ota_start(moduleId)
  │    ├─ ota_start_ack: fail → 展示 error_code / msg，结束
  │    ├─ ota_start_ack: ok   → 等设备主动断开
  │    └─ 没回 ACK 就先断开   → 按已进入 FlashBoot 处理
  │
  ▼
FlashBoot（A5 5A 明文二进制）
  │
  ├─ 用升级前保存的 deviceId 重连（不重新扫描）
  ├─ 等 notify 订阅真正就绪
  ├─ boot 广播 0x10 → APP 回查询帧
  ├─ 设备 0x50 请求 [offset, len] → APP 0x51 回填数据
  └─ 设备 0x20 报状态 → APP 0x21 确认
  │
  ▼
重连正常固件 → 重新 hi → 读目标模块 firmwareVer → 与目标版本一致才算成功
```

这里有一个关键认知：**OTA 是设备拉取模式，不是 APP 推送模式**。

APP 不能自己决定先发哪一段、发多长。设备通过 `0x50` 告诉 APP：“我要 offset 是多少、长度是多少的一段”，APP 再用 `0x51` 把对应的数据回填过去。这个模型决定了后面很多设计：

- 写失败或丢包不需要 APP 盲目重发，设备会按 offset 重新请求；
- APP 如果擅自重发，反而可能产生重复帧，打乱 boot 的流解析；
- “写回调成功”不等于“设备收到”，真正的回执是设备的下一个 `0x50` 请求；
- 传输速度的瓶颈通常在设备写 flash，而不是手机侧。

另外，OTA 的 `moduleId` 来自设备 `device_config` 上报的 `modules` 清单。设备没上报模块，或者模块号取错，后面的流程根本发不起来。这一步看起来不起眼，但联调时经常是“按钮点了没反应”的第一现场。

## 二、坑 1：同一根特征，两套协议

### 2.1 业务是 JSON + AES，OTA 是 A5 5A 明文

业务链路的数据长这样：

```text
JSON → AES-128-ECB → 密文 → 写入特征
设备通知 → 密文 → AES 解密 → 拼 JSON → 按 cmd 分发
```

OTA 链路的数据长这样：

```text
A5 5A 12 <cmd> <帧长 LE 2B> <data> <checksum>
```

两者共用同一个 GATT 特征，设备不会主动告诉你“现在切换到 OTA 协议了”。APP 只能靠帧头判断：第一个字节是 `0xA5`、第二个是 `0x5A`，就按 OTA 原始帧处理；否则继续走 AES 解密和 JSON 拼包。

我们在 `ble_manager` 里加了一个 `_otaRawSink` 旁路：

```ts
// OTA 会话期间，notify 原始字节直接交给 OTA 模块，
// 跳过 AES 解密和 JSON 拼包；OTA 帧是明文，走解密必然失败。
if (_otaRawSink) {
  _otaRawSink(chunk)
  return
}
```

这个旁路必须是“会话级”的：只在 OTA 期间挂上，结束、失败、异常路径都要无条件释放。否则所有业务通知都会被倒进一个已经结束的回调里，页面收不到任何设备消息，只能重连恢复。后来我们干脆把释放放在统一的 `finish()` 里，任何退出路径都经过它。

### 2.2 帧长和校验：别按“数据长度”理解

山景这套帧格式有几个容易写错的地方：

```text
A5 5A 12 <cmd> <帧长 LE 2B> <data...> <checksum>

帧长 = 整帧总字节数（含帧头、命令、帧长、校验）
data 长度 = 帧长 - 7
checksum = (0x100 - sum(除校验位外的所有字节)) & 0xFF
```

“帧长”不是 data 的长度，而是整帧长度。第一次实现时如果按 data 长度填，设备会直接判帧非法。

联调时最好拿 demo 常量做锚点，逐字节对：

```text
查询  A5 5A 12 11 10 00 01 00 00 00 00 00 00 00 00 CD
确认  A5 5A 12 21 10 00 00 00 00 00 00 00 00 00 00 BE
```

只要这两帧和 demo 对不上，先别怀疑设备，先查帧长和 checksum。

### 2.3 字节不是字符串：AES 的 UTF-8 陷阱

我们保留了一个“加密查询帧”探针，用来验证设备侧到底是先解密再识别 OTA 帧，还是直接识别明文。写这个探针时踩了一个很隐蔽的坑：

`crypto-js` 的 `AES.encrypt(plainText, key)` 会把字符串按 UTF-8 解析。OTA 帧里的 `0xA5`、`0x5A` 这类大于 `0x7F` 的字节，如果先转成字符串再加密，会被编码成两个字节，原始帧结构直接坏掉。

正确做法是走 `WordArray` / hex 中转，按字节加密：

```ts
const plainHex = Array.from(bytes)
  .map((b) => b.toString(16).padStart(2, '0'))
  .join('')

const encrypted = AES.encrypt(encHex.parse(plainHex), encUtf8.parse(KEY), {
  mode: ECB,
  padding: Pkcs7,
})
```

这个坑的教训不只适用于 OTA：**只要载荷是二进制，就不要用字符串 API 去加密、拼接或比较**。`A5` 不是字符 `A5`，它是字节 `0xA5`。

## 三、坑 2：deviceId 不是设备身份

### 3.1 Android 的 MAC，iOS 的 UUID

微信 `onBluetoothDeviceFound` 返回的 `deviceId`，在不同平台上含义完全不同：

| 平台    | `deviceId` 的实际含义              | 能不能持久化                                     |
| ------- | ---------------------------------- | ------------------------------------------------ |
| Android | 设备 MAC 地址                      | 相对稳定，但也不建议当业务唯一标识               |
| iOS     | 系统分配的 UUID                    | **不能**。同一会话内稳定，跨手机、跨扫描可能变化 |
| 鸿蒙    | 随系统和机型变化，不能假设等于 MAC | **不能**                                         |

我们一开始也想过“把 `deviceId` 存起来，下次直接连”。在 Android 上可能侥幸能用，在 iOS 上一定出问题：用户换一台手机，或者系统重新分配 UUID，保存的 `deviceId` 就指向了一个不存在的设备。

真正可持久化的身份是广播数据里的 SN。设备的广播格式是：

```text
字节 0~1：公司标识 'FC'
字节 2~3：通道码 '10' / '20'
字节 4~N：SN 的 ASCII
```

扫描时解析出 SN，写入业务字段 `device_id`，列表匹配、自动重连、云端绑定都用它。`deviceId` 只用于“这一次连接”，不进入任何持久化存储。

### 3.2 FlashBoot 不广播身份，重连只能靠保存的 deviceId

正常固件会带 `FC` 广播，FlashBoot 不保证带。协议里写得很清楚：FlashBoot 可能没有正常模式的 `FC20` / SN 广播，名称也可能变。

所以升级途中设备断开后，**不能重新扫描等广播**，只能用断开前保存的 `deviceId` 直接重连。这也是为什么 `deviceId` 虽然不能持久化，但在一次 OTA 会话里必须被可靠保存。

同理，`ota_start_ack` 返回的 `bootName` 只能用于日志核对，不能拿来当连接条件。同名设备可能有好几台，名称也可以被改。

### 3.3 蓝牙名不是身份，UUID 也不是身份

我们早期还按蓝牙名分流 GATT 通道，后来全部推翻了。原因很现实：

- 名称可以改，同名设备可能有多台；
- FlashBoot 的名称和正常固件不同；
- 设备名不承载业务语义，用它判断通道迟早出错。

最终改成按广播里的通道码选 GATT 表：

| 通道码 | 服务 UUID      | 写特征         | 通知特征       | 形态       |
| ------ | -------------- | -------------- | -------------- | ---------- |
| `10`   | `0000ffe0-...` | `0000ffe1-...` | `0000ffe1-...` | 单特征双向 |
| `20`   | `0000ab00-...` | `0000ab01-...` | `0000ab03-...` | 写读分离   |

还要区分三个概念：

- **deviceId**：微信/系统给的连接地址，iOS 上是临时 UUID；
- **service / characteristic UUID**：GATT 寻址用的类型标识，不是设备身份；
- **handle**：协议栈内部给每个 GATT 属性分配的 16 位句柄，iOS 会缓存 UUID 到 handle 的映射。

UUID 相同，不代表 handle 相同。主固件切到 FlashBoot 后，如果属性表的声明顺序或 CCCD 位置变了，同一批 UUID 在 iOS 眼里可能已经指向了旧的 handle。这就是下一节要讲的句柄失效。

另外，服务 UUID 匹配不到时不要直接放弃。我们的做法是退化为“遍历全部服务，用写特征 UUID 反查”，这样固件 UUID 和配置表不完全一致时也能连上，新机型首次联调会省很多事。

## 四、坑 3：iOS 的“连接成功”是假象

### 4.1 connected = true，不代表收得到数据

`createBLEConnection` 成功只说明链路建立了。iOS 的服务发现是异步的，在 `getBLEDeviceServices` / `getBLEDeviceCharacteristics` 完成之前，`notifyBLECharacteristicValueChange` 可能一直报：

```text
The handle is invalid（10008）
```

我们最初就是看到 `connected` 为 true 就开始发查询帧。结果写回调成功了，设备却没有任何回包，最后 30 秒判死。看起来像“设备无响应”，实际上是**手机根本没订阅上通知，设备的应答全落在听不见的窗口里**。

后来加了一个明确的就绪信号 `_notifyReady`：只有 `notifyBLECharacteristicValueChange` 成功，才认为通道可用。OTA 流程不等待 `connected`，而是等待 `waitNotifyReady()`。

### 4.2 句柄失效不会自愈，连接级重连也没用

2026 年 11 月 5 日真机实测，重连 FlashBoot 后订阅通知：

- 重试 10 次 × 600ms，全部报 `The handle is invalid`；
- 断开重连，连续三代连接，句柄依然无效；
- 等一段时间，不会自愈。

这说明问题不在“重试次数不够”，而是 iOS 按外设缓存了主固件的 GATT 属性表。FlashBoot 的属性表换了 handle，但系统还在用旧映射。

我们最后做了两层兜底：

1. **短重试**：3 次 × 600ms。观测证明重试基本不会成功，窗口保持短，尽快升级手段；
2. **适配器级重建**：`closeBluetoothAdapter → 300ms → openBluetoothAdapter → 重连 → 重新发现服务 → 重新订阅`，最多 2 次，逼微信丢弃会话级 GATT 缓存。

需要诚实地说：适配器级重建也不是万能药。iOS 系统层 `bluetoothd` 的缓存不保证随微信重启清除。如果两次重建后仍报 10008，小程序侧已经没有更多手段，只能从固件侧解决：

- 让主固件和 FlashBoot 的 GATT 属性表对齐（声明顺序、特征值/CCCD 句柄一致）；
- 或者实现 GATT 的 Database Hash（`0x2B2A`）/ Service Changed（`0x2A05`），让 iOS 主动重新发现服务。

我们在错误提示里把这条链路写清楚了，避免后来的人以为是“小程序重试没写够”。

### 4.3 通知特征不能只看 UUID，还要看 properties

还有一个更隐蔽的坑：通知特征 UUID 命中了，但那个特征根本没有 `notify` / `indicate` 属性，或者没有 CCCD。iOS 在这种特征上订阅，同样会报 `The handle is invalid`。

所以选通知特征时不能只按 UUID 找，必须看属性：

```ts
const canNotify = (c) => !!(c.properties?.notify || c.properties?.indicate)

const uuidMatch = chars.find((c) => c.uuid.toLowerCase() === channel.notifyCharId.toLowerCase())
const notifyChar =
  (uuidMatch && canNotify(uuidMatch) ? uuidMatch : undefined) ||
  chars.find(canNotify) ||
  uuidMatch ||
  writeChar
```

优先级是：UUID 命中且属性支持 → 任意支持 notify 的特征 → UUID 命中但属性不支持（记录警告）→ 写特征自身（兼容单特征双向）。

这一步在写读分离机型上尤其重要。写特征和通知特征不是同一个，取错一个，表现就是“能写但不能收”。

### 4.4 订阅成功也要打日志

安卓/鸿蒙上，“订阅成功但收不到数据”和“订阅失败”在业务层的表现完全一样：设备没有任何回包。

如果日志里只有“连接成功”，根本无法区分是设备没发、还是手机没听见。所以订阅成功时必须留一行：

```text
[BleManager] 通知订阅成功（第 1 次） service=... char=...
```

这一行在后面的排障里救了很多次。

## 五、坑 4：有响应写 vs 无响应写

### 5.1 两种写模式的本质区别

BLE 的写操作有两种：

| 写模式                      | 是否等 ATT 响应 | 特点                                                                  |
| --------------------------- | --------------- | --------------------------------------------------------------------- |
| `write`（有响应）           | 等              | 每个写都要等设备回 ATT 响应，吞吐受连接间隔限制，但可靠性有协议层确认 |
| `writeNoResponse`（无响应） | 不等            | 写完就交给协议栈，速度快，但可能静默丢包，成功回调不代表设备收到      |

微信 `writeBLECharacteristicValue` 支持 `writeType` 参数。不传时按平台默认：Android 优先无响应写，iOS 优先有响应写。这个默认行为在小数据量业务指令上没什么感觉，但在 OTA 几 MB 的固件上会被放大成几倍的耗时差异。

### 5.2 不要按操作系统判断，按设备声明的能力判断

我们最初想用 `platform` 判断：Android 用无响应写，iOS 用有响应写。后来发现这条路走不通，原因有两个：

- 鸿蒙设备上微信返回的 `platform` 和官方枚举对不上（后面单独讲）；
- 同平台不同机型、不同固件的特征属性也可能不同。

最后改成只看写特征的 `properties.writeNoResponse`：

```ts
const chars = await Taro.getBLEDeviceCharacteristics({
  deviceId,
  serviceId,
})

const wc = chars.characteristics.find((c) => c.uuid.toLowerCase() === writeCharId.toLowerCase())
const noRespSupported = !!wc?.properties?.writeNoResponse
```

设备声明支持，就用 `writeNoResponse`；设备只声明 `write`，就用平台默认。属性查询失败时按“支持”处理，因为查询本身可能偶发失败，而真机实测无响应写在多数目标机型上可用；万一不支持，下一层还有 10007 回退和 3 秒看门狗。

### 5.3 iOS 的 10007：失败发生在下发前，可以安全回退

iOS 上第一次传 `writeNoResponse`，我们遇到过：

```text
10007 / not support
```

关键是这个失败发生在数据真正下发之前，所以同一帧改用平台默认写重发是安全的，不会产生重复帧。我们的处理是：

```ts
if (writeType && /10007|not support/i.test(err.message)) {
  writeType = undefined
  writeModeLabel = '平台默认(无响应写不支持，已自动回退)'
  // 本会话后续统一走默认写，并重发当前帧
  send(frame, label)
}
```

只回退一次，本会话后续都走默认写，避免每一帧都先失败再重试。

### 5.4 无响应写的 success，不是设备回执

这是最容易误判的一点。

有响应写的 `success` 至少代表设备回了 ATT 响应；无响应写的 `success` 只代表数据交给了协议栈。设备有没有收到、有没有写进 flash，协议栈不知道。

所以 OTA 里不能把“写成功”当成“这一包完成”。真正的完成信号是设备的下一个 `0x50` 请求：它请求了新的 offset，说明前面的数据已经被消费；它重新请求同一个 offset，说明前面那段可能丢了。

也正因为如此，我们**不在写超时后自动重发**。设备拉取模式本身会按 offset 补齐，APP 擅自重发会制造重复帧，打乱 boot 的解析。写超时只做 fail-fast：

```ts
const RAW_WRITE_TIMEOUT = 3000

// 单片哨兵：超时后迟到的 success 不能再推进 offset，
// 否则会话结束后仍在往 boot 写数据。
let pieceSettled = false
const timer = setTimeout(() => {
  if (pieceSettled) return
  pieceSettled = true
  callback({ success: false, errMsg: `写入超时（${RAW_WRITE_TIMEOUT}ms 无回调）` })
}, RAW_WRITE_TIMEOUT)
```

### 5.5 超长写入可能永远不回调

iOS 上还有一个官方文档提过、但很容易忽略的行为：超过协商 MTU 的写入，可能既不回调 `success`，也不回调 `fail`。

我们的写链是靠 `success` 推进的。如果某一包永远不回调，整个流程就会停在那里，只能等 30 秒判死。后来加了两道保险：

- 单片 3 秒看门狗，超时即失败退出；
- 严格信任协商 MTU，不再做“MTU 太小就兜底成 240”的反向操作。

之前有一版逻辑是 `chunk > 20 ? chunk : 240`，本意是防止 MTU 读异常，结果如果实际 MTU 只有 23，写 240 字节就会超长，iOS 直接不回调。**兜底值不能超过协商值**，这是一个反直觉但很重要的约束。

## 六、坑 5：鸿蒙的平台字段不可信

鸿蒙是这次最“薛定谔”的平台。

微信官方文档里，`getSystemInfoSync().platform` 的枚举包含 `ohos`。但实测在部分鸿蒙设备上，拿到的值和文档对不上：有时不是 `ohos`，有时干脆拿不到预期值。

如果代码写成：

```ts
if (platform === 'ohos') {
  // 鸿蒙分支
}
```

那这部分逻辑可能永远不会执行。我们最初想按平台决定写模式，就是在这里翻车的。

最后的结论是：**平台字段只能用于展示和日志，不能用于关键能力分支**。要判断能力，用两个更硬的事实：

1. 写特征是否声明 `writeNoResponse`（协议层事实）；
2. `setBLEMTU` 调用是否成功（该 API 仅 Android 有效，调用成功即可断定不是 iOS）。

鸿蒙上还有一个表现：订阅成功但收不到数据。它和订阅失败在业务层看起来一模一样，都是设备无响应。这也是为什么上一节强调“订阅成功必须打日志”。

另外，鸿蒙的联调通道也有坑，而且和 OTA 代码无关：

2026 年 10 月 17 日实测，同一份包：

- 「预览」二维码在 Android / 鸿蒙 / iOS 全部正常；
- 「真机调试」下，鸿蒙所有 `/app-api` 请求 pending 到超时（后端其实已经处理了）；
- iOS 在「真机调试」下启动即 `Maximum call stack size exceeded`。

所以蓝牙联调一律用「预览」，别用「真机调试」。定位口诀也很简单：

```text
[静默登录] 开始 有、请求返回 无
→ 登录响应没回来
→ 后续绑定全部卡住
→ 表现为一直游客模式且没有 /device/bind 请求
```

这是调试通道的问题，不是业务代码的问题。联调时如果一开始就撞上，会白白浪费半天。

## 七、坑 6：时序，早一步晚一步都错

### 7.1 过早接管原始通道，会丢 ota_start_ack

第一版实现里，我们在发 `ota_start` 之前就把 notify 原始通道接管了。当时的想法是：“boot 一上线就会推 `0x10`，必须提前接住。”

这个想法只对了一半。`ota_start` 的应答 `ota_start_ack` 是**正常固件的 JSON 回包**，不是 `A5 5A` 帧。原始通道一接管，JSON 就被跳过了解密和分发，ACK 永远收不到。更糟的是，设备返回 `fail`（比如 TWS 还连着）时，我们也看不到错误，只能按“设备断开了”继续往下走。

协议里写得很清楚：**收到 ACK 之前，APP 保持正常 AES/JSON 解析；收到 `ok` 后再等设备断开；重连 FlashBoot 时才启用原始二进制解析。**

最终时序改成：

```text
ota_start（正常通道，AES/JSON）
  → 等 ota_start_ack
  → 收到 ok，继续用正常解析等断开
  → 在 ble_disconnected 事件里立刻挂上原始通道
  → 自动重连到 FlashBoot
```

### 7.2 过晚接管原始通道，会丢 boot 的第一帧

反过来也不行。如果等“重连成功”之后再挂原始通道，boot 的第一帧 `0x10` 可能已经到了。boot 等不到应答，会自己断开。

这里还有一个事件顺序的细节：`BleManager` 在收到断开事件时，是**先通知监听器，再启动 2 秒自动重连**。所以原始通道必须在 `ble_disconnected` 的监听器里挂上，不能等重连成功后再挂。

```ts
if (msg.cmd === 'ble_disconnected') {
  disconnected = true
  installRawSink() // 先挂通道，再唤醒等待方
  settleGate({ type: 'disconnected' })
}
```

### 7.3 ota_start 要三路等待，不能只等 ACK

设备的行为有三种可能：

1. 回 `ota_start_ack`，`status=ok`；
2. 回 `ota_start_ack`，`status=fail`，带 `error_code` 和 `msg`；
3. 不回 ACK，直接断开。

所以等待逻辑要同时处理 ACK、断开、超时三路：

```ts
type OtaStartGate =
  | { type: 'ok' }
  | { type: 'fail'; reason: string }
  | { type: 'disconnected' }
  | { type: 'timeout' }
```

- `fail`：立即结束，展示设备给的原因，不要继续重试；
- `ok`：等设备断开，15 秒内没断开就报错；
- 先断开：按已进入 boot 处理；
- 超时：结束，并明确提示“不要连续重发 ota_start”。

连续重发 `ota_start` 是一件很危险的事。设备可能已经在切换过程中，第二条请求会把它推进到未知状态。

### 7.4 boot 的 0x10 广播：不能不等，也不能乱答

重连到 FlashBoot 后，不能上来就发查询帧。boot 可能还没就绪，会直接丢掉这一帧；如果随后又把后续的 `0x10` 广播去重掉，设备就会一直重复广播，直到 30 秒判死。

我们的策略是：

1. 先等 boot 的 `0x10` 广播，收到后用查询帧应答；
2. 如果 1.2 秒内没收到广播，再主动发一帧查询作为兜底；
3. 如果此后仍然一帧 OTA 都没收到，每 3 秒重发一次查询，直到收到第一帧为止；
4. `0x10` 连发时做 800ms 去重，但**不做永久去重**。

为什么不能永久去重？因为第一帧查询如果被设备丢了，boot 会继续广播 `0x10`。如果 APP 认为“查询已经发过”而永远不再应答，设备就会一直等到判死。这个坑我们在 OPPO 上实测过，表现就是卡满 30 秒。

为什么又需要去重？因为短时间内连发两帧查询，会让 boot 重启读取序列。我们遇到过两次升级失败，设备反复请求 offset 0，最后解析错位。嵌入式同事还原出来的现场是：

```text
0x0A + 0x0958B656 = 0x0958B660
```

也就是说，包头被 boot 误当成了数据段头。根因就是重复的查询帧打乱了它的流解析。

所以去重窗口要“短到不会重启序列，长到不会漏掉应答”。800ms 是我们实测下来的折中点。

## 八、坑 7：MTU 协商是异步的

### 8.1 读到的 255，不一定是真的

OTA 的传输总耗时大致是：

```text
固件大小 / 单次可写 × 单次写入耗时
```

单次可写直接决定写入次数。我们一开始在重连后立刻 `getBLEMTU`，读到 `255`，就按 `255 - 3 = 252` 切包。后来发现链路实际协商到了 `512`，只是 `setBLEMTU` 还在异步协商中，`getBLEMTU` 读到了协商完成前的旧值。

结果就是：OTA 一直用半带宽传输，写入次数翻倍，升级时间被白白拉长。

修复方式是“先顶到目标，设置失败就等一拍，再读”：

```ts
Taro.setBLEMTU({ deviceId, mtu: target })

if (!mtuSetOk) await sleep(200)

const mtu = await Taro.getBLEMTU({ deviceId, writeType: 'write' })
const chunk = Math.min(509, mtu - 3)
```

- `509` 是 ATT 有效载荷的硬上限，再大也装不下；
- `setBLEMTU` 失败时等 200ms，是因为可能撞上重连流程正在进行的协商；设置成功就直接读；
- `setBLEMTU` 仅 Android 有效，iOS 由系统协商；
- 正常固件和 FlashBoot 的 MTU 可能不同，所以要在**连到 boot 之后**再取，不能在升级前取一次用到底。

### 8.2 setBLEMTU 成功，是一个比 platform 更硬的能力证据

因为 `setBLEMTU` 只在 Android 上有效，我们把它当成“不是 iOS”的判定依据。调用成功，说明当前平台支持 MTU 协商；调用失败，也不一定是 iOS，可能只是当前连接不允许设置。

这比 `platform === 'ios'` 可靠得多，因为它验证的是“能力”，不是“字符串”。

### 8.3 Android 扫描还需要系统定位

顺便记一个 Android 的经典坑：系统定位关闭时，`startBluetoothDevicesDiscovery` 会返回成功，但 `onBluetoothDeviceFound` 永远不回调。

也就是说，代码看起来在扫描，实际上什么都扫不到。我们加了前置检查：

```ts
if (sys.platform === 'android' && !sys.locationEnabled) {
  // 提示用户开启定位服务
  return
}
```

这个坑和 OTA 无关，但配网、设备列表、自动重连都会受影响，值得单独记一笔。

## 九、坑 8：设备“无响应”时，到底是谁没响应

OTA 流程里有一个 30 秒的最终判死：只要 30 秒内没有收到任何合法 OTA 帧，就结束。

但在“30 秒无响应”这个表象背后，至少可能有六种完全不同的原因：

| 表象                   | 实际原因                                        | 怎么区分                               |
| ---------------------- | ----------------------------------------------- | -------------------------------------- |
| 写入成功，设备不回包   | notify 没订阅上 / 10008 句柄失效                | 看“通知订阅成功”日志；没有这行就是没通 |
| 写入一直没有回调       | iOS 超长写入 / 协议栈挂起                       | 看 3 秒单片看门狗的错误                |
| 设备反复推 0x10        | 查询帧发得太早，boot 丢了；或去重挡住了后续应答 | 看 raw 日志里 0x10 的重复次数          |
| 设备请求 offset 0 反复 | 重复查询帧导致 boot 重启读取序列                | 看 0x50 的 offset 序列                 |
| 设备报 0x0303 读取超时 | 前面已经解析错位，APP 还回了空帧                | 看越界 offset 和错误码                 |
| 完全没有任何帧         | 还停留在正常固件；ota_start 失败或超时          | 看 ota_start_ack / 断开事件            |

这张表是这次调试最有用的产出之一。没有 raw 日志，所有问题看起来都像“设备无响应”；有了双向十六进制日志，才能把问题定位到具体一层。

### 9.1 一定要打 build 号

2026 年 11 月 5 日我们遇到过一次混包：弹窗显示的 build tag 是新的，但 OTA 会话里打印的 notify 等待超时还是旧值。也就是说，实际跑的不是最新代码。

后来在 OTA 会话开始的第一行就打印：

```text
OTA 会话开始（build 20261106-1615，notify等待20s/适配器重建）
```

调试面板上也直接显示 build 号，不用开 console 就能确认跑的是不是最新包。这个习惯在真机联调里非常值钱，尤其是多台手机、多个体验版并存的时候。

### 9.2 无响应写 ≠ 设备无响应

这两个词很容易混：

- “无响应写”是 GATT 的 `writeNoResponse`，是一种写模式；
- “设备无响应”是业务层收不到任何回包。

无响应写的 `success` 只代表数据交给了协议栈；设备无响应可能是通知没订阅上、boot 没就绪、查询帧被丢、解析错位。排障时先把这两个概念分开，能少走很多弯路。

## 十、坑 9：传输性能与那些“看起来像设备问题”的细节

### 10.1 每包两条日志，吃掉 3%～13% 的升级时间

OTA 传输一个几 MB 的固件，要往返几千次。我们最初把每条收发日志都写进页面状态，结果每次 `setState` 都要跨桥渲染，实测单次 2～8ms，7000+ 次下来吃掉了升级总时长的 3%～13%。

后来的做法：

- 过程日志只走 `console`，不进页面渲染；
- 进度按 25% 刷新，全程最多 6 次 `setState`；
- 传输结束后一次性弹窗汇总，不依赖页面渲染链路。

### 10.2 用三段耗时定位瓶颈

为了判断慢在手机侧还是设备侧，我们在内存里采样了三段：

```text
A = notify 到达 → 发起写（JS 解析 + 组帧 + 调 API）
B = 发起写 → 写回调成功（跨桥 + 空口）
C = 上次写成功 → 下一个 notify 到达（设备写 flash + 连接间隔空窗）
```

只有算术，没有日志和 UI，传输期开销可以忽略。结束时一次性输出：

```text
分包均值（N 包）：JS 处理 x ms · 写入 y ms · 设备间隔 z ms
```

如果 A 大，优化手机侧；如果 B 大，看写模式和连接参数；如果 C 大，瓶颈通常在设备写 flash，APP 再怎么优化也没用。

### 10.3 速度要按“实际送达字节”算

失败中断时，如果用固件总长除以耗时，会算出一个虚高的平均速度。我们改成按设备请求过的最大 `off + len` 来算，失败时也能看到真实传输了多少。

### 10.4 32 位 offset 不要截断

设备的数据请求里，offset 是 4 字节小端：

```ts
const off = (bytes[6] | (bytes[7] << 8) | (bytes[8] << 16) | (bytes[9] << 24)) >>> 0
const reqLen = bytes[10] | (bytes[11] << 8)
```

早期版本写了 `& 0xffffff`，把高 8 位截掉了。结果真实的越界地址 `0x0958B660` 被打成 `0x58B660`，看起来还在文件范围内，掩盖了解析错位的证据。

正确做法是保留完整 32 位，并且一旦 `off >= firmware.length` 就立即终止：

- 正常流程设备按自身分段结构推进，不会越过文件末尾；
- 越界一定是解析错位；
- 不要回空帧，空帧只会让设备空等重试，最后报 `0x0303` 读取超时。

这次嵌入式同事就是靠完整 offset 还原出了 `0x0A + 0x0958B656 = 0x0958B660`，才定位到“包头被当成数据段头”的根因。

### 10.5 0x20 状态和 0x21 确认

FlashBoot 用 `0x20` 报状态，APP 每次都要回 `0x21` 确认：

| 状态   | 含义          | 后续                           |
| ------ | ------------- | ------------------------------ |
| `0x02` | 准备升级      | 回确认，继续传输               |
| `0x05` | 无需升级      | 回确认，重连核对版本           |
| `0x06` | boot 报告成功 | 回确认，等待重启，重连核对版本 |
| `0x07` | 升级失败      | 回确认，读错误码并提示         |

注意：`0x06` 只是 boot 说“我写完了”，不是最终成功。必须重连回正常固件，重新 `hi`，读目标模块的 `firmwareVer`，和目标版本一致后才显示“升级成功”。

启动 ACK、发完文件、BLE 断开，都不能作为成功依据。

## 十一、复盘清单

把这次踩的坑压缩成一张表：

| 类别     | 最后落地的结论                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份     | iOS 的 `deviceId` 是临时 UUID，不能持久化；持久身份用广播里的 SN；boot 重连用升级前保存的 `deviceId`                                        |
| UUID     | service / characteristic UUID 只用于 GATT 寻址；服务 UUID 匹配不到时遍历服务反查写特征；通知特征必须看 properties，不只看 UUID              |
| 句柄     | `connected=true` ≠ 通知就绪；等 `notifyReady` 再发数据；10008 重试 + 适配器级重建；根因要靠固件对齐属性表或 Database Hash / Service Changed |
| 写模式   | 按 `properties.writeNoResponse` 选，不按 platform；iOS 10007 安全回退一次；无响应写的 success 不是设备回执                                  |
| 时序     | ACK 前保持 AES/JSON；断开事件里立刻挂原始通道；等 0x10 再握手；800ms 去重；3 秒重试直到第一帧                                               |
| MTU      | set → 等 200ms → get；信任协商值，不反向兜底 240；连到 boot 后再取                                                                          |
| 鸿蒙     | platform 字段不可信，用 GATT 能力和 API 结果判断；联调用「预览」，别用「真机调试」                                                          |
| 无响应   | 30 秒判死只是最后一层；先看订阅日志、raw 日志、offset 序列、build 号                                                                        |
| 性能     | 过程日志只进 console；进度最多 6 次 setState；用 A/B/C 三段耗时定位瓶颈                                                                     |
| 成功判定 | 重连正常固件读 `firmwareVer`，一致才算成功                                                                                                  |

还有几个没有完全解决的问题，也一并记下来：

- **iOS 的系统级 GATT 缓存**：小程序侧只能做到适配器重启，清不掉 `bluetoothd` 的缓存。最终需要固件对齐属性表，或者实现 Database Hash / Service Changed。
- **鸿蒙的机型差异**：`platform` 字段和写模式行为在不同版本上仍有差异，目前只能靠“设备声明能力 + 运行时日志”兜底，还需要更多机型验证。
- **无响应写的可靠性边界**：不同协议栈对“成功”的定义不完全一致，唯一可靠的判据仍然是设备的下一个数据请求。

## 写在最后

这次 OTA 最深的感受是：**难点不在协议本身，而在状态机跨了两个固件、两套协议、三种平台和无数层缓存。**

正常固件和 FlashBoot 是两套完全不同的 GATT 属性表、两套数据格式、两套错误语义；iOS 缓存句柄，Android 协商 MTU，鸿蒙的平台字段又不可信；再加上设备拉取模式、重复查询帧、异步订阅这些时序问题，任何一个环节早一步或晚一步，表现都是同一句话——“设备无响应”。

真正把问题拆开的，不是更多的重试，而是更细的观测：

- 双向 raw 日志，能看出设备到底发了什么；
- 订阅成功日志，能区分“没发”和“没听见”；
- build 号，能确认跑的是不是最新包；
- offset 序列，能看出解析有没有错位；
- A/B/C 耗时，能看出瓶颈在手机还是设备。

如果你也在做 BLE OTA，希望这篇记录能帮你少熬几个晚上。至少下次看到 `The handle is invalid` 的时候，可以先想到：不是设备不理你，可能是 iOS 还在用上一套固件的句柄。
